# Raptor News Bot — نسخه V5.7

این بسته شامل پنج فایل اجرایی/تنظیماتی نسخه V5.7 و یک مجموعه آزمون آفلاین است. هستهٔ خبر V5.6 حفظ شده و بخش «محتوای تحلیلی» به‌صورت زیرسامانهٔ مستقل روی آن توسعه داده شده است. داده‌های تحلیلی در `state.json` زیر کلید `_analytics` ذخیره می‌شوند؛ صف و تنظیمات خبر به‌عنوان صف تحلیلی استفاده نمی‌شوند.

> **وضعیت آزمایش:** بررسی نحو Python و آزمون‌های رفتاری آفلاین با پاسخ‌های هوش مصنوعی شبیه‌سازی‌شده انجام شده‌اند. به‌دلیل نداشتن کلید API و محیط ربات شما، اتصال زنده به تلگرام، Gemini، جست‌وجوی وب و دریافت/ارسال واقعی تصویر در این محیط آزمایش نشده است. تضمین «بدون هیچ باگ» صادقانه ممکن نیست؛ قبل از انتشار عمومی از حالت آزمایشی استفاده کنید.

## محتویات بسته

- `bot.py` — هستهٔ ربات، پنل مدیر و چرخهٔ اجرای صف اخبار و تحلیل.
- `analytics.py` — تحقیق، تولید مقاله، تقسیم پست، تصویر، ذخیره‌سازی و زمان‌بندی مستقل تحلیلی.
- `requirements.txt` — وابستگی‌های Python.
- `Procfile` — فرمان اجرای Worker روی Railway.
- `README.md` — همین راهنما.
- `tests/test_upgrade_behaviour.py` — آزمون‌های رگرسیون آفلاین V5.7.

## قابلیت‌های اصلی V5.7

### دو مسیر تولید محتوا

1. **تحقیق از موضوع:** جست‌وجوی وب واقعی از طریق DuckDuckGo، ثبت عنوان/پیوند/خلاصه و زمان دریافت منابع، و تحلیل/نگارش با Gemini. در صورت پشتیبانی مدل، Google Search grounding نیز به درخواست Gemini افزوده می‌شود. مقاله و منابع جدا ذخیره می‌شوند و مقاله پیش از بازبینی مدیر وارد مسیر انتشار نمی‌شود.
2. **تبدیل متن:** پذیرش متن دستی و فایل‌های متنی، Markdown، PDF متنی و DOCX؛ ورودی به مقاله/پست‌های تلگرامی تبدیل می‌شود. PDF اسکن‌شده‌ای که فقط تصویر دارد، بدون OCR قابل استخراج نیست.

Gemini ارائه‌دهندهٔ پیش‌فرض و جدا از تنظیمات AI بخش خبر است. تنظیم مدل از `ANALYTICS_GEMINI_MODEL` خوانده می‌شود و به `GEMINI_MODEL` بخش خبر وابسته نیست. مدیر می‌تواند در تنظیمات تحلیلی Failover خودکار را روشن کند تا پس از ناموفق‌شدن ارائه‌دهندهٔ انتخاب‌شده، ارائه‌دهندگان فعال بعدی طبق ترتیب پنل امتحان شوند. خاموش‌بودن Failover رفتار تک‌ارائه‌دهنده‌ای قبلی را حفظ می‌کند. انتخاب دستی Groq یا Mistral نیز همچنان در دسترس است؛ در درخواست جایگزین، نتایج جست‌وجوی وب اولیه به مدل داده می‌شوند اما Google Search grounding مخصوص Gemini اجرا نمی‌شود.

### مدیریت و اعتبارسنجی پست‌ها

- پروژه‌ها و پست‌ها شناسه و وضعیت مستقل دارند.
- هدف تولید ۵ تا ۶ پست است؛ خروجی کمتر از ۵ فقط با ثبت صریح ناکافی‌بودن متن منبع قابل قبول است.
- محدودیت ۱۰۲۰ نویسه با footer در Python بررسی می‌شود؛ محدودیت کپشن تلگرام برحسب واحد UTF-16 نیز اعتبارسنجی می‌شود.
- footer استاندارد: `#raptor` و `@khaatshekaan`.
- پست‌ها پیش‌نویس می‌مانند تا مدیر آن‌ها را بازبینی و تأیید کند.
- ویرایش، بازنویسی و بازتولید، نسخه‌های قبلی را نگه می‌دارند؛ خطا در تولید پست مانع انتشار خودکار می‌شود.
- امکان مدیریت تصاویر، گالری پروژه، انتخاب/حذف/جابه‌جایی تصاویر، اجازهٔ بدون تصویر برای یک پست مشخص، پیش‌نمایش، انتخاب گروهی، تغییر وضعیت گروهی و تغییر گروهی زمان پست‌های زمان‌بندی‌شده وجود دارد.
- از ۲ تا ۱۰ تصویر می‌توان برای یک پست از قابلیت آلبوم تلگرام استفاده کرد؛ کپشن به تصویر اول متصل می‌شود. تلگرام برای یک Media Group سقف ۱۰ مورد دارد.

### تصاویر و منابع

جست‌وجوی تصویر از Wikimedia Commons انجام می‌شود. سامانه فقط URLهای مستقیم HTTPS از `upload.wikimedia.org` با MIME تصویری شناخته‌شده را نگه می‌دارد و قابلیت دریافت را بررسی می‌کند؛ بااین‌حال ارتباط تصویری/شرح/مجوز و مناسب‌بودن تصویر باید قبل از استفاده توسط مدیر بررسی شود. نتایج تصویر در ابتدا گزینه‌های پیشنهادی‌اند و بی‌تأیید مدیر به پست متصل نمی‌شوند. تصاویر ارسالی مدیر نیز با `file_id` تلگرام در گالری همان پروژه ذخیره می‌شوند.

### زمان‌بندی مستقل

- منطقهٔ زمانی پیش‌فرض محتوای تحلیلی `Asia/Tehran` است و با `ANALYTICS_TIMEZONE` قابل تغییر است.
- بازهٔ پیش‌فرض زمان‌بندی ۱۴:۰۰ تا ۲۱:۰۰ است؛ حداقل فاصلهٔ برنامه‌ریزی‌شده با زمان‌های خبری ۲۰ دقیقه است.
- زمان‌بندی خودکار یا دستی از پنل انتخاب می‌شود. زمان دستی پیش از ذخیره با محدودیت‌ها اعتبارسنجی می‌شود.
- موتور تحلیل فقط زمان‌های خبر را **می‌خواند** و هیچ خبر را حذف یا جابه‌جا نمی‌کند. با ورود خبر جدید، فقط پست تحلیلیِ خودکار می‌تواند باززمان‌بندی شود؛ زمان دستی برای بازبینی مدیر علامت‌گذاری می‌شود.
- چون موتور خبر در این نسخه الزاماً تمام زمان‌های آیندهٔ خبر را به‌صورت رکورد زمان‌بندی‌شده نگه نمی‌دارد، بخشی از زمان‌های خبری آینده از روی بازه‌ها و فاصلهٔ انتشار تنظیم‌شده در پنل خبر **پیش‌بینی** می‌شود. این زمان‌های پیش‌بینی‌شده خبر قطعی یا تضمین‌کنندهٔ فاصلهٔ دقیق نیستند؛ سامانه هنگام رسیدن زمان انتشار دوباره تعارض شناخته‌شده را بررسی می‌کند.
- توقف/ادامهٔ صف تحلیلی به صف خبر دست نمی‌زند. هر روز حداکثر یک پروژهٔ تحلیلی در زمان‌بندی خودکار انتخاب می‌شود؛ پروژه‌های بعدی در صف باقی می‌مانند.

### کنترل خطا و جلوگیری از ارسال مجدد

- رکورد انتشار پیش از درخواست ثبت می‌شود؛ اگر نتیجهٔ ارسال مبهم باشد، وضعیت `uncertain` می‌گیرد و ارسال خودکار دوباره انجام نمی‌شود.
- برای یک پیام منتشرشده، ویرایش متن از مسیر edit همان پیام انجام می‌شود و پیام جدیدی نمی‌سازد. در صورت خطای مبهم ویرایش نیز وضعیت بررسی دستی ثبت می‌شود.
- اگر پست با خطای ارسال مواجه شود، وضعیت و علت در پروژه نگهداری می‌شود.
- فایل state خراب نباید کورکورانه با ساختار خالی جایگزین شود؛ هستهٔ ربات قابلیت پشتیبان‌گیری از فایل خراب و توقف در این حالت را دارد.
- به‌روزرسانی پروژه‌ها در فضای `_analytics` از فیلدهای صف خبر جدا می‌ماند.

## نصب و استقرار روی Railway

1. از `state.json` و Volume موجود نسخهٔ پشتیبان بگیر.
2. پنج فایل اصلی (`bot.py`، `analytics.py`، `requirements.txt`، `Procfile` و `README.md`) را در ریشهٔ سرویس Worker قرار بده؛ پوشهٔ `tests/` برای اعتبارسنجی آفلاین است و در اجرا لازم نیست.
3. فقط **یک Worker/Replica** اجرا کن تا polling تلگرام و نوشتن state هم‌زمان نشوند.
4. Railway Volume را به مسیر `/data` متصل و `STATE_FILE=/data/state.json` تنظیم کن.
5. متغیرهای محیطی را در Railway Variables تنظیم کن. توکن‌ها را در کد یا چت قرار نده.

### متغیرهای اصلی

از همان متغیرهای بخش خبر نسخهٔ فعلی استفاده کن؛ مقادیر واقعی محرمانهٔ خودت را در Railway نگه دار:

```env
BOT_TOKEN=YOUR_TELEGRAM_BOT_TOKEN
OWNER_TELEGRAM_ID=YOUR_NUMERIC_TELEGRAM_USER_ID
TARGET_CHAT_ID=@khaatshekaan
SOURCE_CHANNELS=MaxOsintIntel,OSINTWarfare,defenseexpressua,WarPeaceAndYou,RazmAvaran_org,defence_news

GROQ_API_KEYS=YOUR_GROQ_KEY
GROQ_MODEL=openai/gpt-oss-120b
GEMINI_API_KEYS=YOUR_GEMINI_API_KEY
GEMINI_MODEL=gemini-3.8-flash
MISTRAL_API_KEYS=YOUR_MISTRAL_KEY
MISTRAL_MODEL=mistral-small-latest

POLL_INTERVAL_SECONDS=180
STATE_FILE=/data/state.json
TEST_MODE=true
```

### متغیرهای محتوای تحلیلی

```env
ANALYTICS_GEMINI_MODEL=gemini-3.8-flash
ANALYTICS_TIMEZONE=Asia/Tehran
ANALYTICS_TARGET_CHAT_ID=@khaatshekaan
```

- `ANALYTICS_GEMINI_MODEL` فقط مدل بخش تحلیلی را کنترل می‌کند.
- `ANALYTICS_TIMEZONE` منطقهٔ زمانی زمان‌بندی تحلیلی است.
- `ANALYTICS_TARGET_CHAT_ID` مقصد پست‌های تحلیلی است؛ اگر تنظیم نشود، از `TARGET_CHAT_ID` استفاده می‌شود.
- `TEST_MODE=true` انتشار واقعی را مسدود می‌کند و برای آزمون اولیه توصیه می‌شود.
- کلیدهای چندگانهٔ هر API را با کاما در متغیر مربوطه قرار بده، بدون فاصله یا خط جدید.

قیمت، سقف استفاده و سهمیه‌های Gemini و قابلیت Google Search grounding به نوع حساب و سیاست‌های فعلی سرویس بستگی دارند و ممکن است تغییر کنند. فعال‌کردن API یا جست‌وجوی grounded لزوماً به معنی دسترسی رایگان یا نامحدود نیست.

## آزمون و بررسی پیش از انتشار واقعی

ابتدا نحو فایل‌ها و آزمون‌های رگرسیون را بررسی کن:

```bash
python -m py_compile bot.py analytics.py
python -m unittest discover -s tests -v
```

سپس با `TEST_MODE=true` از گفت‌وگوی خصوصی ربات دستور `/admin` را اجرا کن و این موارد را دستی بررسی کن:

1. ساخت پروژهٔ متنی و پروژهٔ تحقیقاتی؛
2. مشاهدهٔ منابع و مقاله، بازبینی/رد/تأیید مقاله؛
3. تولید ۵ تا ۶ پست، اعتبارسنجی تعداد کاراکترها و footer؛
4. ارسال چند تصویر به پروژه، انتخاب تصاویر و پیش‌نمایش؛
5. تأیید هر پست به‌صورت جداگانه و آزمایش زمان‌بندی در حالت خودکار و دستی؛
6. راه‌اندازی مجدد Worker و بررسی باقی‌ماندن پروژه‌ها و زمان‌ها؛
7. تأیید اینکه صف خبر و زمان‌بندی خبرها تغییری نکرده است.

فقط پس از بازبینی محتوای آزمایشی و آماده‌بودن کلیدها، `TEST_MODE=false` را فعال کن و ابتدا یک پست کم‌ریسک را کنترل‌شده منتشر کن.

## محدودیت‌های صریح نسخه

- هیچ آزمون زنده‌ای با حساب Railway یا توکن واقعی Telegram/Gemini در این بسته انجام نشده است.
- جست‌وجوی وب و تصویر، نتیجهٔ تضمین‌شدهٔ بی‌نقص نمی‌دهند؛ مدیر باید کیفیت و اعتبار منابع و مجوز/ارتباط تصاویر را بازبینی کند.
- متادیتای منتشرشده و بازدید کانال از Bot API معمولی همیشه در دسترس نیست. آمار این بخش مبتنی بر داده‌های ذخیره‌شدهٔ ربات است و آمار رسمی کامل کانال محسوب نمی‌شود.
- OCR برای PDF اسکن‌شده، ویرایش مستقیم تصویرِ یک پست از قبل منتشرشده، و مشاهدهٔ تضمینیِ تاریخچهٔ کامل پیام‌هایی که قبل از ثبت شناسه در state وجود داشته‌اند، در این نسخه ارائه نشده‌اند. متن پیام منتشرشده در صورت داشتن شناسه و دسترسی لازم قابل ویرایش است.
- چون ارسال به تلگرام و ذخیرهٔ فایل state یک تراکنش مشترک اتمیک ندارند، نتیجهٔ نامشخص به‌طور کامل قابل حذف نیست؛ در این حالت ربات از retry خودکار خودداری می‌کند تا مدیر وضعیت کانال را بررسی کند.

## تغییرات ارتقا به V5.7

### موتور خبر

- متن نهایی عمومی پیش از انتشار از نام/یوزرنیم کانال‌های منبع و الگوهای صریح «به نقل از کانال» پاک‌سازی می‌شود؛ اطلاعات منبع همچنان برای پنل و تاریخچهٔ مدیریتی حفظ می‌شود.
- وزن هدف سبد ایران به ۴۵٪ افزایش یافته است؛ سبدهای خبر منطقه‌ای، روسیه-اوکراین، تسلیحاتی بین‌المللی و خبر جهانی نیز سهم مستقل دارند تا پوشش بین‌المللی حفظ شود. این عدد هدف ترکیب و امتیازدهی صف است، نه سهمیهٔ سخت یا تضمین انتشار دقیق ۴۵٪ خبر ایران؛ موجودی منابع، کیفیت و ارزش خبری همچنان بر انتخاب نهایی اثر می‌گذارند.
- خبرهای صرفاً مربوط به خرید/رونمایی/تحویل تسلیحات بین‌المللی با جریمهٔ اولویت مواجه‌اند؛ خبرهای عملیاتی و درگیری همچنان امتیاز رویدادی خود را حفظ می‌کنند.
- آستانه‌های تشخیص تکرار عادی کاهش سخت‌گیری پیدا کرده‌اند. در حالت جنگ، آستانه‌ها بالاترند تا فقط شباهت بسیار نزدیک به‌عنوان تکرار حذف شود؛ کلید رویداد به‌تنهایی برای حذف خبر کافی نیست.
- در حالت جنگ، فاصلهٔ زمان‌بندی تحریریه و محدودیت سقف روزانه کنار گذاشته می‌شود و صف واجد شرایط به‌صورت دسته‌ای تخلیه می‌شود. یک فاصلهٔ فنی کوتاه برای رعایت محدودیت‌های انتقال تلگرام باقی می‌ماند؛ این فاصله، تایمر تحریریه نیست.
- انتخاب کلیدهای Groq میان کلیدهای در دسترس متعادل‌تر شده و برای خطاهای 429/موقت، cooldown هر کلید با backoff و Retry-After مدیریت می‌شود. لاگ موفقیت دیگر شناسهٔ کلید را ثبت نمی‌کند.
- هشدارهای مستقیم مربوط به تمام‌شدن/غیرفعال‌بودن ارائه‌دهندگان AI حذف شده‌اند؛ هشدارهای عملیاتی دیگر مانند قطع منبع، صف غیرعادی یا نبود انتشار طولانی‌مدت باقی می‌مانند.
- آرشیو خبرهای ردشده با سقف ۵۰۰ مورد اضافه شده است. مدیر می‌تواند هر مورد را بررسی و با تأیید دستی، بدون عبور دوباره از فیلتر تکرار، به ابتدای صف بازگرداند.

### محتوای تحلیلی

- Failover خودکار در مسیر تحلیلی به‌صورت گزینهٔ مستقل اضافه شده است. در صورت فعال‌سازی، ابتدا ارائه‌دهندهٔ انتخاب‌شده و سپس ارائه‌دهندگان فعال پنل، مطابق ترتیب پیکربندی‌شده امتحان می‌شوند. انتخاب دستی ارائه‌دهنده همچنان حفظ شده است.
- صف پایدار AI به‌صورت گزینهٔ مستقل اضافه شده است. اگر این گزینه روشن باشد و ارائه‌دهندهٔ مجاز به‌دلیل نبود کلید/محدودیت موقت/خطای سرویس در دسترس نباشد، پروژهٔ تحقیق یا تبدیل متن در `state.json` ثبت می‌شود و بدون ورود دوبارهٔ موضوع/متن، در چرخه‌های بعدی دوباره تلاش می‌شود.
- کارهای تحلیلی که Worker هنگام وضعیت `processing` روی آن‌ها متوقف شود، پس از ۵ دقیقه به صف انتظار بازگردانده می‌شوند.
- هر دو گزینه در پنل «محتوای تحلیلی ← تنظیمات تحلیلی» قرار دارند و برای حفظ رفتار قبلی، در مهاجرت اولیه خاموش‌اند؛ مدیر باید آن‌ها را به‌صورت آگاهانه روشن کند. صف انتظار، خطاهای موقت/نبود ارائه‌دهنده را نگه می‌دارد؛ خطاهای دائمی مانند درخواست نامعتبر یا مجوز ردشده نیازمند اصلاح کلید/تنظیمات هستند و خودکار به‌عنوان خطای موقت بی‌نهایت تکرار نمی‌شوند.

### پنل مدیریت

- آمار منابع در مدیریت منابع قرار گرفته؛ تحلیل عملکرد و خروجی CSV در آمار و وضعیت ربات قرار دارند.
- قوانین تأیید خودکار، بلاک‌لیست، کلیدواژه‌های اولویت و سکوت موضوعی در مسیر تنظیمات قرار دارند.
- توقف‌های موقت و حالت‌های عادی/جنگ زیرمنوهای جدا دارند. صف انتشار در مدیریت اخبار باقی مانده و از منوی اصلی به‌عنوان ورودی تکراری حذف شده است.
- مسیر دستور `/admin` برای نمایش سریع منو از قفل طولانی پردازش خبر جدا شده است؛ این اصلاح پاسخ‌گویی فرمان را در زمان انتظار چرخهٔ خبر بهبود می‌دهد، اما جایگزین بررسی خطاهای Polling یا تداخل چند Worker نیست.

### تنظیمات اختیاری

دو متغیر اختیاری پروفایل جنگ: `WAR_MAX_PUBLISH_PER_CYCLE=30` و `WAR_TRANSPORT_GAP_SECONDS=1.1`. در حالت عادی این دو متغیر اثری ندارند. مقدار فاصلهٔ فنی در کد بین ۰٫۸ تا ۲ ثانیه محدود شده است.

هیچ وابستگی Python جدیدی برای V5.7 اضافه نشده است. ساختار state به‌صورت افزایشی ارتقا پیدا می‌کند: صف تحلیلی در `_analytics.ai_queue` و آرشیو ردشدگان خبر در `_rejected_news` ذخیره می‌شوند؛ داده‌های قدیمی حذف یا بازنویسی نمی‌شوند. با این حال، پیش از استقرار از Volume و `state.json` نسخهٔ پشتیبان تهیه کن.

### نکتهٔ استقرار

این بسته به Railway، توکن تلگرام یا APIهای واقعی متصل نشده است. پیش از استقرار روی سرویس اصلی، یک نسخهٔ آزمایشی با Volume جدا و `TEST_MODE=true` اجرا کن. برای polling تلگرام فقط یک Worker/Replica فعال باشد. اگر لاگ‌ها متوقف شدند یا `/admin` جواب نداد، Metrics، وضعیت Deployment و لاگ‌های جدید را جداگانه بررسی کن.

## V5.8 reliability and event lifecycle upgrade

V5.8 adds `reliability.py`, a persistence-friendly helper module integrated into `bot.py`:

- Stable `event_id` based on the existing normalized event key, distinct from the text fingerprint used for exact/near-duplicate checks.
- Queue lifecycle metadata (`DISCOVERED`, `SCORED`, `APPROVED`, `SCHEDULED`, `PUBLISHING`, `PUBLISHED`, plus `RETRY`, `REJECTED`, `QUARANTINED`, `CANCELLED`) and bounded lifecycle history.
- Explainable heuristic score breakdown fields for operational importance, balance-of-power impact, novelty, audience value, and confidence. These fields are heuristic proxies, not fact verification.
- Runtime health snapshot persisted after successful main cycles: process uptime, source-check/cycle timestamps, recent cycle error, last publish timestamp, queue stale counts, memory peak and PID.
- Admin diagnostic output now includes the health snapshot and warnings for stale source-check or queued items.

### Safety and deployment notes

- `state.json` is backward-compatible: new fields are added lazily to existing queue records and state version is advanced to 5.8.
- This helper intentionally does **not** automatically resend a stale `sending` item. Telegram delivery may have succeeded even if the worker lost the response; automatic retry can create duplicate posts. Such items should be resolved via the existing uncertain-delivery manager flow.
- Automatic process restart is not initiated from inside the bot. Configure Railway restart policy as the process supervisor; an in-process self-restart can create polling conflicts or repeated crash loops. The health snapshot supports detection and diagnosis, but Railway metrics (CPU/RAM) still must be read from Railway's platform telemetry.
- Queue lifecycle fields are metadata and do not replace the existing delivery status/fingerprint mechanism.
